# Процесс разработки Wallet_4i7 в GitHub с несколькими агентами

Дата: 12 сентября 2026 года  
Статус: проект на письменной проверке  
Связанная задача: GitHub Issue #2

## 1. Цель

Wallet_4i7 разрабатывается через GitHub несколькими агентами и с разных устройств. Репозиторий должен оставаться единственным источником истины, а каждое изменение — иметь понятную цель, автора, историю обсуждения, результаты проверки и безопасный способ интеграции.

Процесс должен одновременно решать четыре задачи:

1. не допускать потери или случайного перезаписывания чужой работы;
2. позволять нескольким агентам работать параллельно;
3. сохранять архитектурные и продуктовые решения вместе с кодом;
4. обеспечивать воспроизводимую передачу работы между устройствами и агентами.

## 2. Основные принципы

- GitHub является источником истины для кода, документации, задач и решений.
- Ветка `main` содержит только проверенные и принятые изменения.
- Прямые коммиты и push в `main` запрещены.
- Одна задача оформляется как одна Issue, одна рабочая ветка и один Pull Request.
- Каждый агент работает в отдельном Git worktree и отдельной ветке.
- Локальные незакоммиченные изменения не считаются переданной работой.
- Агент не отменяет, не перезаписывает и не переносит чужие изменения без явного согласования.
- Небольшие регулярные коммиты и push предпочтительнее крупных локальных пакетов изменений.
- Любое значимое архитектурное решение фиксируется в ADR до или одновременно с реализацией.

## 3. Язык проекта в GitHub

На русском языке ведутся:

- README и проектная документация;
- Issues, Pull Requests и Discussions;
- описания коммитов после технического префикса;
- комментарии к проверкам и передаче работы;
- ADR, runbook и отчёты об инцидентах;
- пользовательские тексты продукта, если иное не определено локализацией.

На английском языке остаются технические идентификаторы:

- имена файлов, каталогов, веток и пакетов;
- названия классов, функций, переменных, API и полей данных;
- стандартные типы Conventional Commits: `feat`, `fix`, `docs`, `test`, `refactor`, `chore`, `ci`, `build`, `perf`, `revert`;
- точные названия сторонних технологий и протоколов.

Пример корректного коммита:

```text
docs(workflow): описать передачу задачи между агентами (#2)
```

## 4. Единица работы

Каждое изменение начинается с GitHub Issue. Issue содержит:

- цель и ожидаемый результат;
- границы задачи и явно исключённые изменения;
- критерии приёмки;
- предполагаемые области и файлы;
- зависимости от других задач;
- ответственного агента или владельца;
- ссылку на архитектурное решение, если оно требуется.

Связь артефактов выглядит так:

```text
Issue → рабочая ветка → отдельный worktree → коммиты → Pull Request → проверки → review → merge
```

Нельзя объединять несколько независимых продуктовых задач в один Pull Request. Если в ходе работы обнаружена отдельная проблема, для неё создаётся новая Issue.

## 5. Именование веток и worktree

Формат ветки:

```text
<type>/<issue-number>-<short-slug>
```

Допустимые типы:

- `feat` — новая возможность;
- `fix` — исправление ошибки;
- `docs` — документация;
- `refactor` — изменение структуры без изменения поведения;
- `test` — тесты;
- `chore` — инфраструктурная работа;
- `security` — отдельное изменение безопасности.

Примеры:

```text
feat/12-live-theme-editor
fix/27-motion-reduced-mode
docs/2-agentic-workflow
```

Локальные worktree размещаются в игнорируемом каталоге:

```text
.worktrees/<issue-number>-<short-slug>
```

Один worktree принадлежит одной ветке. Два агента не должны одновременно использовать один worktree или вносить изменения в одну рабочую ветку.

## 6. Начало работы агента

Перед изменением файлов агент обязан:

1. прочитать корневой `AGENTS.md` и локальные инструкции в затрагиваемых каталогах;
2. выполнить `git fetch --prune origin`;
3. убедиться, что Issue свободна либо явно передана ему;
4. оставить в Issue комментарий о начале работы;
5. указать имя ветки, предполагаемые файлы и границы изменения;
6. создать ветку от актуального `origin/main`;
7. создать отдельный worktree;
8. проверить чистое состояние и запустить доступные базовые проверки.

Рекомендуемый комментарий о начале работы:

```text
Беру задачу в работу.

Ветка: feat/12-live-theme-editor
Область: packages/tokens, apps/theme-studio
Не изменяю: backend, custody, CI
Планируемая проверка: unit-тесты, typecheck, визуальная проверка
```

Если базовые тесты уже падают, агент не продолжает молча. Он фиксирует исходный сбой в Issue и отделяет его от результатов своей работы.

## 7. Параллельная работа нескольких агентов

Перед параллельным запуском задача декомпозируется по независимым границам. Хорошее разделение:

- один агент работает над design tokens;
- второй — над UI-компонентами, используя согласованный контракт tokens;
- третий — над документацией или тестовой инфраструктурой.

Плохое разделение:

- два агента одновременно переписывают один компонент;
- один агент меняет контракт API, пока другой независимо строит на старом контракте;
- несколько агентов коммитят в одну ветку без координации.

Для каждого параллельного потока в Issue или связанной подзадаче указываются:

- владелец;
- ветка;
- затрагиваемые каталоги;
- входной и выходной контракт;
- порядок интеграции зависимых Pull Request.

Если двум задачам требуется изменить один файл, владелец общего файла определяется заранее. Второй агент передаёт требуемое изменение владельцу либо ждёт интеграции первого Pull Request.

### Сквозные и структурные изменения

Изменение дерева каталогов, общих контрактов, маршрутизации всего сайта или базовой конфигурации считается сквозным. Для него действуют дополнительные правила:

1. создаётся отдельная Issue с картой затрагиваемых каталогов и зависимых веток;
2. при архитектурных последствиях до реализации принимается ADR;
3. в связанных Issues публикуется временная отметка `ожидает структурное изменение`;
4. назначается один агент-интегратор, владеющий перемещениями и общими контрактами;
5. структурное изменение оформляется отдельным Pull Request без несвязанных продуктовых функций;
6. в Pull Request приводится карта `старый путь → новый путь` и инструкция обновления зависимых веток;
7. после merge остальные агенты получают новый `origin/main`, обновляют свои ветки и повторно запускают проверки.

Два независимых структурных Pull Request не должны одновременно менять одну область дерева. Второй Pull Request блокируется явной зависимостью от первого либо декомпозируется так, чтобы области не пересекались.

## 8. Работа с разных устройств

Работа может продолжаться на другом компьютере только после публикации состояния в GitHub.

Перед завершением сессии агент:

1. сохраняет логически завершённые изменения отдельными коммитами;
2. запускает относящиеся к задаче проверки;
3. выполняет push рабочей ветки;
4. оставляет в Issue комментарий передачи;
5. указывает последний commit SHA, выполненные проверки, известные ограничения и следующий шаг.

Шаблон передачи:

```text
Передача работы

Ветка: feat/12-live-theme-editor
Последний коммит: abc1234
Готово: схема токенов и runtime-применение четырёх цветов
Осталось: тест reduced-motion и документация API
Проверки: unit 18/18, typecheck успешно
Важно: файл packages/tokens/schema.ts не менять до объединения PR #14
Следующий шаг: добавить тест режима reduced-motion
```

На новом устройстве работа начинается с `git fetch --prune origin` и checkout опубликованной ветки. Нельзя восстанавливать состояние по памяти или копировать рабочий каталог вручную поверх другой версии репозитория.

## 9. Синхронизация с `main`

- Рабочая ветка создаётся от актуального `origin/main`.
- Перед открытием или обновлением Pull Request агент повторно получает изменения из `origin/main`.
- История опубликованной ветки не переписывается, если её использует другой агент.
- Force push запрещён по умолчанию.
- Синхронизация выполняется контролируемым merge или rebase только владельцем ветки; выбранный способ указывается в Pull Request.
- Конфликтующие изменения разбираются по смыслу, а не автоматическим выбором одной стороны целиком.

После разрешения конфликта повторно запускается полный набор проверок Pull Request.

## 10. Коммиты

Каждый коммит должен быть небольшим, логически целостным и пригодным для отдельного review.

Формат:

```text
<type>(<scope>): <описание на русском> (#<issue>)
```

Требования:

- заголовок описывает результат, а не процесс;
- один коммит не смешивает форматирование, рефакторинг и новую функциональность;
- временные сообщения `wip`, `tmp`, `fix stuff` не используются в итоговой истории;
- сгенерированные файлы коммитятся только вместе с источником и командой воспроизведения;
- секреты и персональные данные не попадают в историю даже временно.

## 11. Pull Request

Pull Request открывается рано как Draft, если другим агентам нужен видимый контекст. Перед переводом в состояние Ready for review он содержит:

- ссылку на Issue;
- краткое описание результата;
- список существенных решений;
- перечень затронутых областей;
- результаты тестов, сборки, typecheck и lint;
- скриншоты или видео для визуальных изменений;
- риски, ограничения и план отката;
- отметку об обновлении документации;
- отдельный блок по безопасности для auth, custody, платежей и данных.

Автор Pull Request не объединяет его, пока обязательные проверки не завершены успешно и замечания review не закрыты.

## 12. Защита `main`

Для `main` вводятся следующие правила GitHub:

- изменения только через Pull Request;
- обязательное успешное прохождение CI;
- обязательное отсутствие неразрешённых review threads;
- запрет force push и удаления ветки;
- требование актуальности ветки относительно `main` перед merge;
- предпочтительный способ объединения — squash merge;
- заголовок squash-коммита соответствует формату Conventional Commits и написан на русском после префикса.

До появления второго постоянного reviewer допускается самопроверка владельцем проекта, но статус проверок и доказательства тестирования остаются обязательными.

## 13. Архитектурные решения

Значимые решения оформляются в `docs/adr/` отдельными ADR. ADR требуется, если изменение:

- определяет технологический стек или крупную зависимость;
- меняет границу модулей;
- влияет на безопасность, custody, ledger или аутентификацию;
- изменяет публичный контракт API;
- создаёт долгосрочное ограничение для white-label платформы.

ADR содержит контекст, рассмотренные варианты, принятое решение, последствия и статус. Старый ADR не переписывается для сокрытия истории: новое решение заменяет его новым ADR со ссылкой на предыдущее.

## 14. Структура проектной документации

Планируемая структура:

```text
README.md
AGENTS.md
CONTRIBUTING.md
SECURITY.md

.github/
├── ISSUE_TEMPLATE/
│   ├── feature.yml
│   ├── bug.yml
│   └── architecture.yml
└── pull_request_template.md

docs/
├── architecture/
├── adr/
├── product/
├── runbooks/
├── security/
└── superpowers/
    └── specs/
```

Назначение основных файлов:

- `README.md` — назначение проекта, быстрый старт и карта документации;
- `AGENTS.md` — обязательные операционные правила для любого агента;
- `CONTRIBUTING.md` — процесс работы для людей и агентов;
- `SECURITY.md` — безопасное сообщение об уязвимостях и обращение с секретами;
- `docs/architecture/` — актуальное устройство системы;
- `docs/adr/` — неизменяемая история архитектурных решений;
- `docs/product/` — продуктовые сценарии и критерии приёмки;
- `docs/runbooks/` — воспроизводимые эксплуатационные процедуры;
- `docs/security/` — модель угроз и security-требования.

## 15. Безопасность и запрещённые действия

Агентам запрещено:

- коммитить `.env`, токены, приватные ключи, seed-фразы и credentials;
- хранить реальные банковские или пользовательские данные в fixtures и скриншотах;
- помещать private keys в frontend, backend общего назначения или базу приложения;
- выполнять destructive Git-команды для удаления чужой работы;
- использовать `git reset --hard`, force push или удаление веток без явно согласованной необходимости;
- отключать проверки ради успешного merge;
- смешивать visual configuration с правилами финансовой авторизации.

Обнаруженный секрет считается скомпрометированным: он немедленно отзывается, после чего очищается история и документируется инцидент.

## 16. Разрешение конфликтов и восстановление

При пересечении работ:

1. оба агента останавливают изменения в конфликтующей области;
2. в Issue фиксируются ветки, коммиты и затронутые файлы;
3. назначается один ответственный за интеграцию;
4. выбирается порядок объединения Pull Request;
5. второй агент обновляет свою ветку после интеграции первого;
6. проверки выполняются заново.

Если агент обнаружил незнакомые локальные изменения, он считает их чужой работой и не удаляет. Сначала определяется источник через `git status`, `git diff`, историю ветки и соответствующие Issues.

## 17. Критерии готовности изменения

Изменение считается готовым к merge, когда:

- выполнены критерии приёмки Issue;
- изменение находится в отдельной ветке и связано с Pull Request;
- тесты и статические проверки прошли успешно;
- визуальные изменения имеют материалы для review;
- документация и ADR обновлены при необходимости;
- секреты и чувствительные данные отсутствуют;
- ветка синхронизирована с `main`;
- замечания review закрыты;
- в Pull Request описаны риски и способ отката.

## 18. Внедрение правил

После письменного утверждения этой спецификации в Issue #2 должны быть созданы:

1. корневой `AGENTS.md` с обязательными короткими правилами;
2. `CONTRIBUTING.md` с полным рабочим процессом;
3. `SECURITY.md`;
4. русскоязычные шаблоны Issues и Pull Request;
5. начальная структура `docs/` и шаблон ADR;
6. GitHub ruleset для защиты `main`, если возможности аккаунта позволяют его применить;
7. документированная проверка процесса через тестовый Pull Request.

## 19. Границы этой спецификации

Документ определяет процесс разработки и совместной работы. Он не выбирает технологический стек кошелька, не проектирует custody, ledger, backend API или пользовательские экраны. Эти решения оформляются отдельными спецификациями и ADR в рамках Issue #1 и последующих задач.
