# Предлагаемое дополнение: координация Novex

Статус: предложение, не действующая корневая инструкция.

Не копировать этот файл в `AGENTS.md` и не заменять им существующие правила. Корневая workflow-область закреплена за Issue #2 / Draft PR #3; перенос возможен только после согласованного handoff владельца этой области. Сверять текст с текущим handoff, вложенными инструкциями и явными разрешениями владельца. Ни роль, ни этот текст не выдают разрешений на remote-записи или merge автоматически.

## Роли и границы

Владелец принимает продуктовые/визуальные решения. Координатор ведёт задачи и интеграцию. Исполнитель делает назначенную задачу. Reviewer проверяет конкретный diff и не объявляет визуальное решение утверждённым за владельца.

Не становиться координатором по умолчанию: выполняй назначенную роль. Полный протокол — `docs/coordination/README.md`. Skill координатора — `.agents/skills/novex-coordinator/SKILL.md`.

## Перед изменениями

- Прочитай Issue, исходный бриф, последнюю поправку и handoff. Проверь revision задания и назначение владельца.
- Проверь remote ref, полный base SHA, PR base и собственную рабочую папку. Не начинать автоматически от main: дизайн-разработка может находиться в ещё не слитой ветке.
- Одна задача — одна Issue, одна принадлежащая исполнителю ветка и изолированный worktree/clone. Не работать двум пишущим агентам в одной папке/ветке.
- Незнакомые локальные изменения не удалять, не stash-ить и не включать в свой commit.
- Сохраняй режим задания: DESIGN_ONLY не превращается в реализацию; LAB_IMPLEMENTATION не меняет основной кошелёк.

## Во время работы

- Править только назначенные пути. При потребности выйти за scope сначала сообщить координатору и получить обновление задания.
- AGENTS.md, lockfile, manifests, глобальные CSS, exports и общие контракты имеют одного назначенного писателя. Новая зависимость требует согласования, а не параллельного обновления lockfile.
- Не перезапускать занятую задачу и не считать отсутствие сообщений доказательством остановки другого агента.
- Для значимого motion применять reference-first: изучить подходящие реализации, примерить отдельно, сохранить выбранную версию. Не подменять качество примитивным эффектом ради простоты.
- Не создавать/редактировать изображения без прямой просьбы владельца. Логотип не выдумывать.
- Никаких реальных денежных операций, секретов, seed-фраз или настоящих пользовательских данных в рамках дизайн-задач.

## Передача и интеграция

- Сообщи Issue, revision, ветку, полный HEAD, diff, проверки с окружением, ограничения и следующий шаг. Укажи, опубликован ли commit.
- Незапущенный тест обозначай «не проверено», а не «успешно». Существующий чужой отчёт — не собственный прогон.
- Визуальное решение привязывается к версии реализации и preset/hash; тесты не заменяют художественного утверждения.
- Draft PR, выбор визуального варианта, готовность к интеграции и merge — разные состояния.
- Не force-push-ить, не менять чужой PR base, не сливать/закрывать задачи и не публиковать наружу без соответствующего явного разрешения.
- Сборка нескольких PR на проверочной ветке требует отдельного разрешения и проверки совместного результата; она не считается принятием в main.
- Новая сессия восстанавливается из GitHub. Файлы в другой ветке и новые инструкции в другом окне не считаются автоматически полученными; укажи реально прочитанный guidance SHA.
