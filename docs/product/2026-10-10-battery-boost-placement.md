# Батарейка возле конкретной операции

10.10.2026. Предложение для следующего этапа. Подписка или разовый boost могут предоставлять возможность; маленький знак у исходящего платежа должен отражать подтверждённое использование именно в нём. Тарифы не утверждены; backend API подключается позже и сейчас не является приоритетом.

Runtime этой задачи ограничен удалением домашнего trigger и процента. Общая оценка, privacy, закрепления, финансовые данные и существующие demo fee flows сохраняются. Новые boost badges, DTO, fixtures или API здесь не реализуются.

## Возможность и использование

«Доступно» относится к supplied праву воспользоваться услугой в определённом контексте. «Используется» и «использовано» относятся к supplied состоянию конкретной операции. Подписка не доказывает применение boost к каждому платежу; покупка разовой возможности тоже не доказывает её применение.

Статусы платежа pending/completed/failed остаются самостоятельными. Подтверждённое использование boost не означает успешный перевод. Завершённый перевод не доказывает, что boost использовался. Покрытие комиссии не доказывает ускорение; даже наличие оценки ожидания не устанавливает причину или выигрыш во времени.

## Минимальный контракт смысла, без проектирования API

Для будущего marker нужны только авторитетное состояние использования и привязка к stable operation ID, точным source account/asset/network IDs. Состояния: unknown/not-used/active/used. Active/used требуют подтверждения именно этой операции и понятной актуальности данных; произвольного client flag недостаточно. Доступность услуги и источник права — подписка/разовая возможность — остаются отдельными от состояния платежа.

Отсутствие данных не равно not-used. Незнакомое значение, несовпавшие IDs, устаревшая активность или противоречие дают unknown. Старое подтверждение другой session/операции/сети не применяется к новому платежу. Транспорт, названия DTO, расход/возврат услуги и тарифы здесь не определяются.

До такого контракта в существующей истории нет boost marker. Подтверждение использования услуги также не является доказательством сокращения сетевого времени: текст «ускорено» требует отдельно обоснованного смысла услуги.

## Предлагаемое размещение и поведение

Один existing SVG battery glyph 14–16 CSS px в строке метаданных исходящего платежа, рядом с сетью/счётом. Использовать контур из ProductBatteryLine: тело и cap, без процента и без выдуманного уровня заряда. Не ставить знак на сумму, вместо статуса, в отдельную карточку или отдельную обведённую кнопку. При отсутствии marker не резервировать под него пустое место.

| Supplied состояние | История операции | Квитанция и доступное описание |
| --- | --- | --- |
| available без подтверждения использования | Без знака использования | При необходимости право объясняется в контексте услуги; не утверждать, что оно применено к платежу |
| unknown/отсутствует/невалидно | Без знака и без placeholder | Если открыт контекст услуги: «Использование буста пока не подтверждено» |
| not-used | Без знака использования | «Буст не использован», только если это явно supplied факт |
| active и актуальное подтверждение | Маленький glyph; один короткий спокойный отклик при новом подтверждённом событии, затем покой | «Буст используется». Финансовый статус остаётся отдельным |
| used и подтверждение | Статичный glyph | «Буст использован». Pending/completed/failed сохраняются как предоставлены |

Marker показывается только в исходящей проекции для подтверждённой source стороны. Входящая проекция внутреннего перевода и обмен не получают его автоматически. Применимость услуги к внутренним переводам требует отдельного подтверждения, не расширения нынешних bindings.

SVG декоративный, aria-hidden=true; полное доступное описание строки и видимый текст квитанции передают состояние словами. Цвет может поддерживать различие, но не заменяет текст или финансовый статус. Объяснение открывается нажатием уже существующей строки и её деталей. Нельзя вкладывать отдельную интерактивную battery кнопку в интерактивную строку; необязательный hover-only tooltip не является единственным объяснением.

Отклик active использует существующие motion tokens и выполняется один раз по новой версии подтверждения, не по каждому render и не постоянным loop. Для reduced-motion — сразу статичный знак. used всегда статичен. Не добавлять countdown, обещания ETA, свет на финансовых цифрах или новую motion-систему. Противоречие active с завершённым/неуспешным платежом до согласования его смысла трактуется как unknown: не превращать его в used и не запускать движение.

## Вопросы перед реализацией marker

1. Что даёт boost: приоритет обработки провайдера, особый сетевой способ отправки или только покрытие комиссии? Кто может подтвердить применение и что означает active/used?
2. Как право из подписки/разовой покупки ограничено счётом, активом, сетью и видом операции? Как определяется факт not-used, а не отсутствие данных?
3. Что происходит с использованием/возвратом услуги при отказе, отмене или повторе платежа? Как поставщик передаёт исправления и актуальность подтверждения? UI не решает эти правила самостоятельно.

Для будущей визуальной frontend-примерки разрешён UI-пилот active/used с явно демонстрационными состояниями, без API и без утверждений о применении boost к старым платежам. Авторитетные данные, правила реального использования и тарифы нужны перед реальным применением, а не для показа двух вариантов значка. В текущей задаче marker не реализуется: runtime по-прежнему ограничен удалением домашней батарейки.
