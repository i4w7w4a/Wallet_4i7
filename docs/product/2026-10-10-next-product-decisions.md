## P1 — из конкретного счёта найти pending и вернуться

**Ценность.** Пользователь открывает нужный счёт, видит его незавершённые операции, проверяет нужную квитанцию и возвращается к этому же счёту. Ему не приходится выходить на главную или выбирать рабочий счёт ради просмотра истории.

**Подтверждённый пробел.** У [ProductAccountsWorkspace](../../apps/miniapp/src/mono-product/accounts-workspace/product-accounts-workspace.tsx) нет activities/status/retry или callback для pending. В [mono-scene](../../apps/miniapp/src/mono-preview/mono-scene.tsx) `openPendingActivity` допускает только `rootOverview`, а origin просмотра истории поддерживает только `pending-home`. `enterHistory` закрывает Accounts workspace. Поэтому новый вход нельзя объявить готовым только потому, что существует домашний N1.

История в [ProductAssetWorkspace](../../apps/miniapp/src/mono-product/asset-workspace/product-asset-workspace.tsx) уже работает с выбранным активом/размещением. Она не заменяет сводку всех pending счёта: выбор одного актива исключает остальные, а операция может существовать без текущего holding.

**Точная оставшаяся дельта: один законченный путь.**

1. В detail конкретного счёта переиспользовать текущую компактную строку N1. Предлагаемое место — после сводки счёта, перед размещениями; это локальная примерка для владельца, не решение встречи. Список счетов и групповое закрепление не превращать в новый список операций.
2. Получать account scope через существующий `scopeProductActivities`, учитывая обе стороны internal transfer и commerce legs. Считать уникальные event IDs; не сужать по holdings, закреплениям, возможности Send или активности счёта. Один event не раздваивается на source/destination.
3. Single открывает актуальную точную квитанцию; many — существующую History с явным account scope и pending-фильтром. Использовать прежние metadata, demo marker, loading/error/retry и ready-zero поведение. Не делать второй receipt или вторую историю.
4. Сохранить origin конкретного account detail, исходную группу при её наличии и launcher. Back возвращает в этот detail с фокусом. При удалённом счёте/смене session — безопасный существующий fallback, без открытия другого ID. Inspection не вызывает `useAccount` и не меняет источник следующей операции.
5. Сохранить guards, raw drafts и privacy. Status race проверяется по актуальным данным: завершённую запись можно открыть с её текущим результатом; неизвестный/неоднозначный ID даёт недоступность. Отказ guard не оставляет частично изменённую навигацию.

**Данные и решения для выполнения.** Использовать уже supplied demo activities/status/retry и существующие account/event IDs. Backend-ответы для этого локального UX-среза не требуются. Позицию строки и возврат из History подтвердить на локальной примерке; supplied pending не даёт основания показывать ручную проверку, SLA или ETA, если соответствующих полей нет.

**Подходящий owner.** Один SOL MAX исполнитель Accounts/History navigation, назначенный ORCHESTR WALL после завершения Task 2 и заморозки его source: обе дельты затрагивают `mono-scene.tsx`. Предполагаемые области — Accounts workspace, узкий history-origin/Back путь сцены и целевые интеграционные проверки. Core/fixtures, Send/Receive, финансовые ports и presets не входят в этот срез. Точные owned paths определяет исполнитель до записи.

**Критерий законченности.** При другом рабочем счёте инспекция показывает только pending выбранного счёта; single/many открывают правильный scope и event; Back/focus возвращают в исходный detail. Проверены old pending + newer completed, internal участники без двойного счёта, 0/loading/error, удалённый ID/status race и guard отказ. На 320/390 строка читается; суммы и assistive money text сохраняют нынешнюю privacy. Эти проверки относятся к будущему выполнению, здесь они не запускались.

**Пока не делать.** Не вводить стадии/manual-review reason, активацию счетов, whitelist/security gates, тарифы, boost badges, реальные адреса, provider Buy/withdrawal или live adapter. Отсутствие transfer capability не означает отсутствие истории. Demo-ready не становится обещанием серверной полноты.

## Один порядок продолжения

Закончить и принять текущие батарейку/меню → назначить описанный account-specific pending срез → принять связный переход счёт → операция → тот же счёт. Новые UX-задачи выбирать по следующему подтверждённому пробелу, а не автоматически заполнять очередь до трёх пунктов.

Provider Buy, метод вывода фиата, whitelist и security остаются описанными во встрече границами будущих операций. API согласуется позже с backend-разработчиком; нынешний proposal сохраняется ссылкой. Новая техническая матрица или список backend-вопросов в эту очередь не добавлены.

## Ограничения свидетельств

Использован прежний private handoff `review_sol_ultra`: все 404 готовые Deepgram-реплики и выборочный визуальный разбор, без повторного ASR или извлечения медиа. Полное независимое прослушивание и авторские речевые отметки не восстановлены. Поэтому предложение о входе из счёта остаётся предложением аналитика; неизвестную речь нельзя превращать в согласие клиентки. Старый handoff отражает прежний code checkpoint и сохраняется как историческое свидетельство; актуальные завершённые этапы и прямые решения владельца перечислены выше.

Source, runtime, presets, сервер и GitHub этой подготовкой не менялись. Публичное состояние указано по существующей документации, без нового live probe.
